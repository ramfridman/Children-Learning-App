## Security design (security-engineer, to be confirmed by the owner)

- Month and year live in a new local table `ProfileBirths` in the encrypted database (schema v9 to v10), not on `Profiles` (sync, the picker and the tutor read that). Stage P1 to P4 and age are computed in memory.
- The band comes from the school stage, never from the age in months (otherwise `updated_at` on the server would reveal the birth month). `tutor-turn` keeps only `band`; neither the stage nor the school stage goes to Anthropic.
- Server: one additive column `app.child_profile.school_stage` (nullable, check on the six values); `child-put` takes an optional `school_stage`, absent keeps the stored value, anything else is refused. Order: database, then functions, then the app.
- Each September the parent card proposes the next stage; nothing changes until the parent confirms. No change at a birthday or mid-lesson; changes apply at the next session start; age never takes a skill away.
- Controls: fake family server refuses unknown keys; `plan` pinned to `lesson:<id>` / `session:[ABC]`; structural log rule plus a canary test (a birth month never appears in any outgoing request, log or sync payload); delete removes the `ProfileBirths` row; iOS database folder excluded from iCloud backup before any iOS build carries B-29.
